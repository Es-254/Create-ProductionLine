## 2. 架构演进（需求 → 定稿）

### 2.1 原始 SRS（已被取代）

立项 SRS 定义**四个模块**：`ProductionComputer`（计算机）、`ProductionController`（控制器）、
`DataCable`（数据线）、`LineScheme`（方案），配套 **FSM 状态机** + **数据线通信协议**，
配方来源为 **JEI 必装**，QA 用例 TC-01~TC-05（含 TC-03 断线 5 tick 内 ERROR、TC-04 多步顺序执行）。

**决策点（已确认）**：Mod ID `create_productionline`、包名 `com.create.productionline`、一次性全量开发、
先用占位贴图、允许联网拉 Create dev 依赖。

### 2.2 定稿架构（2026-09-06 起，现行）

用户历次决议后，**控制器与数据线模块整体删除**（类、贴图、lang 键、FSM、数据线协议全部移除），
改为"计算机 + 方案 + 16 格加载柜 + 破拆机"：

```
产线计算机(3格: 目标/载体/剪贴板) ──计算──▶ 产线方案(LineScheme NBT + 内嵌 CreateRecipes 缓存)
        │
        └─ 客户端先解析配方 JSON 送服务端，服务端以实时 RecipeManager 重新推导

方案加载柜(16格, 只收真方案) ──按 recipeId 服务端重推导(RecipeDeriver)──▶ cpl_converted 数据包并集 + /reload

破拆机(2格) ──按 recipeId 服务端解析真实输入──▶ 退还原料 + 只读镜像(纯文本)
```

**三个"唯一入口"**（后续改动的锚点）：

| 职责 | 唯一实现 |
| --- | --- |
| 配方推导（顺序 / 产物 count / 可安装条目） | `recipegen/RecipeDeriver`（计算机与加载柜共用） |
| 是否装配类 | `RecipeDescriptor.isAssemblyLikeCategory`（`RecipeDeriver.isConvertibleAssembly` 在其上加 `create:mechanical_crafting`） |
| 配方 JSON 读取（保序、保 `#tag`） | `util/RecipeJsonReader` |

**随之失效的旧 QA 用例**：TC-03（断线检测）、TC-04（控制器多步 FSM）不再适用；TC-01/02/05 保留并落地。

### 2.3 立项期已识别的根本性风险（仍然成立）

**"任意配方 → Create 设施序列"本质是启发式**：绝大多数第三方模组的配方没有统一语义，不可能做到真正通用。
立项时的对策是"内建规则 + 可配置映射字典(JSON) + 特征提取"三层策略，并坚持
**无法映射时明确报"无法映射"，绝不硬凑**（即 TC-01）。
当前实现的落点：`MappingDictionary`（24 条内建 + config 覆盖）+ `RecipeAnalyzer` 特征 + `MachineSelector` 选机。

## 4. 关键技术结论（反编译 Create 6.0.10）

- **序列装配由机器驱动**：物品带/不带 `SEQUENCED_ASSEMBLY` DataComponent 决定匹配；每步由对应机器执行
  （`create:deploying` → 机械手）；`advance()` 未到终点返回过渡物 + 组件，末步 `rollResult()` 结算。
- **机械手执行前置**：USE 模式、`FACING=DOWN` 位于传送带上方、有旋转动力、手持非空；每步消耗手持物 1 个。
- **过渡物必须可跟踪进度**：`GenericIntermediateItem extends SequencedAssemblyItem`（与 Create 自带
  "未完成品"同源），否则中间物会卡住。
- **转换规则**：单机工艺类 → 扁平 `create:<type>`；合成/装配类 → `create:sequenced_assembly`
  （`ingredient`=基底，`transitional_item`=通用中间产物，每个追加原料一个 deploy 步，`loops=1`，产物 count 保留）；
  原生 `create:mechanical_crafting` → **额外**生成不冲突的序列配方；`assemblyMode=mechanical` 时才走机械合成。
- **单一顺序来源**：方案与内嵌配方共用一份"JSON 行优先、保标签"的材料列表，从结构上杜绝基底/步骤错位。
- **标签保真**：源配方 tag 原样写成 `{"tag":…}`，任何同标签成员都能匹配（这是"子弹 48 发可合"的关键）。
- **GUI**：三个界面槽位皮肤**运行时引用** Create `AllGuiTextures`（`client/CreateGui`），不打包 Create 资源。

## 5. 安全模型（服务端为唯一权威，2026-09-07 落地并复核成立）

| 环节 | 实现 | 行为 |
| --- | --- | --- |
| 容器白名单 | `ClipboardCompat.isLoaderCarrier`（`:83`） | 加载柜只认真 `LineSchemeItem`；纸/剪贴板/镜像/伪造 NBT 一律拒收（槽位 `SchemeLoaderMenu:52`、BE 收集 `SchemeLoaderBlockEntity:100`） |
| 加载柜服务端推导 | `SchemeLoaderBlockEntity.currentEntriesMap:93-120` | 按 `RecipeId` → `ServerRecipeLookup.findById:53` 取**实时配方** → `RecipeDeriver.derive:48` 重推导安装条目；解析不到直接跳过 |
| 破拆机权威退款 | `DismantlerBlockEntity.revert:58-141` | 四重守卫：真 `LineSchemeItem`(:64-68) → 槽 0 物品 id == 方案 `OutputItem`(:79-82) → `recipeId` 服务端可解析且产物一致(:86-98) → 含 `#tag` **整单拒绝**(:100-108)；先消费 1 份再退还(:112-129)，最后放镜像(:130-138) |
| 网络入口 | `ModPayloads.handleDismantle:87-89` | 先 `menu.stillValid(player)` 再触碰槽位 |
| 镜像纯文本化 | `LineSchemeMirrorItem:29,42-76` | 只写 `LineSchemeMirror` 展示快照，结构上不含可执行 `LineScheme`/内嵌配方；`isCarrier` 对其返回 `false`(:64) |

**计算入口同规则（2026-09-13 落地，原 M1 已修）**：计算包现在携带真 `recipeId`
（`network/ModPayloads.java` 的 `ComputerComputePayload`；客户端 `ClientRecipeResolver.recipeIdOf()`
把资源键 `ns:recipe/x.json` 还原成配方 id），服务端**不接受任何客户端字段为权威**：

1. `ProductionComputerBlockEntity.runCompute()` 先用 `ServerRecipeLookup.findById` 在实时 `RecipeManager`
   上重新解析该 `recipeId`，并且**只在其产物集合包含目标槽物品 id 时**才采纳，输入一律取服务端版本；
2. 校验失败则回退到服务端全量反查（`findDetailed`）；
3. 只有服务端一个配方都找不到时，才把客户端数据当作**仅用于生成方案**的兜底——此时
   `authoritative=false`，**不推导任何可安装配方**（`processSource` 里已加此闸门），因此伪造包最多得到一个
   演示性方案，无法向世界数据包注入配方。
4. `ModPayloads.handleCompute` 补了 `menu.stillValid(player)`，失效 GUI 不会被执行。

顺带根治了旧 M1 的第二个后果：由于现在用的是**真 recipeId**，`RecipeJsonReader.resultCount` /
`shapedMaterialOrder` 按 `recipe/<id>.json` 反查可以命中，**×N 倍率与网格形状不再静默降级**。

## 9. 已核查确认"干净"的部分（勿重复审计）

以下各项在历次审计中逐条核对过，**当前代码依然成立**，后续审计可直接跳过：

- **构建链路**：编译 0 错误，无 TODO/FIXME/`@Deprecated`；`System.out` 仅存在于 `qa/SelfTest`（启动参数门控）。

  `isSafeFileName` 白名单（`CreateRecipePack:311-316`）；贡献文件重建时逐条过滤。
